# /cmp-merge — Сравнение и объединение конфигураций

Автор: **WNX** · Версия: 1.0 · Статус: рабочий

Контролируемое обновление модифицированной конфигурации 1С. Трёхстороннее сравнение
XML-выгрузок (база / предок / цель) даёт классификацию объектов, оценка коллизий
определяет масштаб ручного разбора, генератор собирает файл настроек сравнения и
объединения (ПНСО) по эталону из платформы и профилю политики. ПНСО применяется
в окне сравнения и объединения при обновлении из CFU (или при объединении из полного CF).

## Виды конфигураций (алиасы)

| Код | Каноническое имя | Алиасы (EN / RU) | Термин платформы | Роль в процессе | Источник | Каталог |
|-----|------------------|------------------|------------------|-----------------|----------|---------|
| `B` | **base** — основная | база, текущая, наша, main / основная конфигурация | `MainConfiguration` | Конфигурация, которую обновляем (с доработками). «Доработали мы» = `P↔B` | XML-выгрузка из конфигуратора (`Файл → Выгрузить конфигурацию в файлы`) | `B/` |
| `T` | **target** — целевая | цель, вторая, файл поставки / целевая версия | `SecondConfiguration` | Полная конфигурация целевой версии. «Изменил вендор» = `P↔T` | XML-выгрузка из полного `1Cv8.cf` целевой версии (загрузка в пустую базу → выгрузка в файлы) | `T/` |
| `P` | **vendor** — предок | поставщик, предок, чистая версия / конфигурация поставщика | `OldVendorConfiguration` | Чистая версия поставщика, на которой реально стоит база. Точка отсчёта | XML-выгрузка из чистого `1Cv8.cf` версии-предка (дистрибутив вендора; версия должна совпадать с конфигурацией поставщика базы) | `P/` |
| `E` | **etalon** — эталон | эталонный файл, образец | — | Файл настроек, сохранённый вручную из диалога платформы для той же пары версий. Даёт шапку, Parameters и точечные решения | Конфигуратор: окно сравнения-объединения → «Действия → сохранить настройки» | `etalon/` |
| `M` | **merge-settings** — ПНСО | настройки, файл настроек объединения | XML `http://v8.1c.ru/8.3/config/merge/settings` | Результат: правила объединения. Применяется при обновлении из CFU / объединении из CF | Генератор скилла | `merge-settings.xml` |

## Требования к окружению

- Python 3.10+; для подкоманды `collisions` — пакет `merge3` (`pip install merge3`).
- Сам скрипт платформу 1С не использует — она нужна только на этапах выгрузки XML-каталогов
  (конфигуратор) и применения ПНСО (окно сравнения и объединения при обновлении из CFU).
- Скрипт кроссплатформенный; пути задаются параметрами, никаких фиксированных каталогов.

## Рабочая папка задачи

Структура задачи — относительная, создаётся в любом рабочем каталоге (пример ниже —
Windows; на другой ОС аналогично):

```
<workdir>/<Задача>\
├── STATUS.md          # контекст, решения, открытые вопросы
├── B\                 # XML-выгрузка основной конфигурации (базы)
├── T\                 # XML-выгрузка целевой версии
├── P\                 # XML-выгрузка версии-предка (поставщика)
├── etalon\            # эталонный файл настроек от платформы
├── out\               # отчёты и кэши хэшей (classification.json, collisions.json, ...)
└── merge-settings.xml # генерируемый ПНСО
```

## Использование

Скрипт: `${CLAUDE_SKILL_DIR}/scripts/cmp_merge.py` (Python 3.10+; для `collisions` нужен пакет `merge3`).

```bash
# 1. Классификация объектов (md5-индексация с кэшем в out/)
python cmp_merge.py classify --b <B> --p <P> --t <T> --out-dir <out>

# 2. Коллизии в модулях (.bsl): merge3(base=P, a=B, b=T) — построчные регионы
python cmp_merge.py collisions --b <B> --p <P> --t <T> --out-dir <out>

# 3. Структурный разбор XML-файлов, изменённых обеими сторонами (узлы/свойства)
python cmp_merge.py xml-collisions --b <B> --p <P> --t <T> --out-dir <out>

# 4. Генерация ПНСО: шапка и точечные решения — из эталона, массовые — по профилю политики
python cmp_merge.py generate --etalon <etalon.xml> \
    --classification <out>/classification.json \
    --out-file merge-settings.xml \
    --vendor-full "Report.РегламентированныйОтчет" \
    --summarize "Role."
```

Результаты: `out/classification.json` (классы vendorOnly / newInT / baseOnly / conflict /
deletedInT + карты файлов по объектам), `out/collisions.json` (коллизии модулей),
`out/xml_collisions.json` (XML-коллизии), `merge-settings.xml` (ПНСО).

## Профиль политики (конфигурационно-специфичное)

Ядро правил универсально; в профиле задаются только массовые решения по классу
`conflict` (остальные конфликты остаются на дефолте платформы — «наш приоритет»):

- `--vendor-full "префиксы"` — объекты, отдаваемые вендору целиком
  (`GetFromSecondConfiguration`). Типовой случай: области, обновляемые вендором
  независимо и не дорабатываемые (регламентированная отчётность).
- `--summarize "префиксы"` — объекты, объединяемые с приоритетом основной
  (`MergePrioritizingMainConfiguration`). Типовой случай: права ролей — суммирование
  (вендорские права на новые объекты входят, коллизии — наши). Дефолт: `Role.`.
- Эталонные записи уровня `Property` (дважды изменённые свойства с принятыми решениями)
  воспроизводятся из эталона как есть; эталон имеет приоритет над массовыми правилами.

## Правила слияния (ядро, универсальные)

- **R0. Гранулярность** — единица слияния не объект и не файл, а: модуль (`.bsl`) —
  процедура/функция → строки (трёхсторонний diff с предком P); XML метаданных — узел свойства;
  форма — узлы `Form.xml` + модуль формы; неделимое (макеты, картинки) — «или-или»
  с приоритетом основной.
- **R1. Независимые изменения** обеих сторон применяются автоматически (разные процедуры,
  узлы, строки).
- **R2. Дедупликация** — идентичные после нормализации (пробелы, экранирование, порядок
  атрибутов XML) версии строки/узла берутся один раз.
- **R3. Вставки вендора встраиваются**: вендорская правка добавляет строки/узлы, наша правка
  их не затрагивает → вендорский блок включается даже внутри «нашей» процедуры; наша часть
  остаётся.
- **R4. Прямая коллизия** (обе стороны изменили одно место): приоритет основной конфигурации,
  вендорская версия — в отчёт коллизий с контекстом.
- **R5. Проверка «не противоречит нашей логике»** для каждой вендорской вставки возле
  коллизии: лексическая независимость (вставка не обращается к изменённым нами символам
  контекста и наоборот), структурная целостность (вставляется целиком, не рвёт наш блок),
  компилируемость после слияния. Не прошло — не применяется автоматически, уходит в отчёт
  с предложением склейки.
- **R6. Метаданные** — поэлементно: добавления обеих сторон суммируются; изменение одного
  узла обеими — приоритет основной + отчёт; составы типов — объединение множеств.

## Верификация применения (обязательные контрольные точки)

После применения ПНСО на тестовой базе выгрузить результат в каталог `R` и проверить:
`R↔T` — вендорские новшества вошли; `R↔B` — наши доработки живы; компиляция всех
изменённых модулей; версия конфигурации сменилась (обработчики обновления запустятся).

## Опыт применения (пример прогона; путь/цифры — конкретный случай, на работу скилла не влияют)

Референс: конфигурация «УСО2» (1С-Рарус), переход 2.5.22.131 → 2.5.22.145.

Объектов ~24 000, файлов ~133 000 на дерево. Классификация: vendorOnly 564, newInT 69,
baseOnly 6188 (из них существенных 5218, только справки 970), conflict 874
(360 регл. отчётность + 514 прочих), deletedInT 0. Коллизий в модулях — 0 (2063 вендорских
.bsl внутри конфликтных объектов вошли автоматически); реальные XML-коллизии — ~25 файлов
(5 DefinedTypes + Document.RegisterRecords — эталонные; ExchangePlans/EventSubscriptions —
только вендор; Roles — суммирование; Configuration.xml — точечный разбор). ПНСО — 384 записи.
Сверка с эталоном 6/6. Шаблоны выгрузки сравниваются md5; различия справок (help-HTML) на
тысячах объектов — возможный шум сериализации разных платформ.

## Важно

- «Конфигурация поставщика» есть в базе, только если конфигурация на поддержке;
  выгружать её из базы штатно нельзя — предок берётся из дистрибутива вендора той же версии.
- CFU не является конфигурацией: его нельзя сравнивать/выгружать; полная конфигурация
  целевой версии получается из полного `.cf` (или из CFU через тестовую базу версии-предка).
- В файл настроек записываются только решения, отличающиеся от поведения по умолчанию;
  доработанные объекты «не трогаются» отсутствием записей, а не запретами.
- Шапка ПНСО (`version="1.2"`, `platformVersion`) и `Parameters` воспроизводятся из эталона
  байт-в-байт; порядок секций важен.
- `AllowMainConfigurationObjectDeletion=true` (как в эталоне платформы) — разрешает удаление
  объектов основной конфигурации при объединении.
